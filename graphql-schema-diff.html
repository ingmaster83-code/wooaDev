GraphQL 스키마 비교 · 호환성 검사

이전과 새 GraphQL SDL 을 비교해 타입·필드·인자·enum 값·유니언·인터페이스 변경을 깨짐, 위험, 안전으로 분류합니다. 응답 필드와 입력 인자는 타입 강화 방향이 반대라는 점까지 반영해 판정합니다.

사용 예시

⛔ 깨지는 변경 8건 · 위험 4건

입력 — 이전 스키마 (SDL)

type Query {
  user(id: ID!): User
  users(role: Role, limit: Int = 10): [User!]!
  legacy: String
}
type User {
  id: ID!
  name: String
  email: String!
  role: Role!
  age: Int
}
enum Role { ADMIN EDITOR VIEWER }
input Filter { text: String, active: Boolean }
union Result = User | Post
type Post { id: ID! }
interface Entity { id: ID! }

입력 — 새 스키마 (SDL)

type Query {
  user(id: String!, expand: Boolean!): User
  users(role: Role, limit: Int = 25): [User]
  version: String
}
type User implements Entity {
  id: ID!
  name: String!
  email: String
  role: Role!
  nickname: String
}
enum Role { ADMIN EDITOR GUEST }
input Filter { text: String!, active: Boolean, tag: String }
union Result = User | Post | Comment
type Post { id: ID! }
type Comment { id: ID! }
interface Entity { id: ID! }

결과 — 변경 사항

판정 | 위치 | 변경
⛔ 깨짐 | Query.user(id) | 인자 타입 ID! → String!
⛔ 깨짐 | Query.user(expand) | 인자 추가 (필수)
⛔ 깨짐 | Query.users | 타입 [User!]! → [User]
⛔ 깨짐 | Query.legacy | 필드 제거
⛔ 깨짐 | User.email | 타입 String! → String
⛔ 깨짐 | User.age | 필드 제거
⛔ 깨짐 | Role.VIEWER | enum 값 제거
⛔ 깨짐 | Filter.text | 타입 String → String!
⚠️ 위험 | Query.users(limit) | 기본값 10 → 25 (인자를 생략한 호출의 결과가 달라짐)
⚠️ 위험 | User | 인터페이스 Entity 구현 추가 (… on Entity 쿼리의 결과가 달라질 수 있음)
⚠️ 위험 | Role.GUEST | enum 값 추가 (클라이언트의 switch 가 처리하지 못할 수 있음)
⚠️ 위험 | Result | union 멤버 Comment 추가 (클라이언트가 새 타입을 처리해야 함)
✅ 안전 | Query.version | 필드 추가
✅ 안전 | User.name | 타입 String → String! (더 엄격한 보장)
✅ 안전 | User.nickname | 필드 추가
✅ 안전 | Filter.tag | 입력 필드 추가 (선택)
✅ 안전 | Comment | type 타입 추가

결과 — 요약

⛔ 깨짐 8건 · 위험 4건 · 안전 5건
판정 기준: 응답 필드는 타입이 더 엄격해지면(T → T!) 안전하고 느슨해지면(T! → T) 깨지며, 입력(인자·입력 필드)은 반대입니다. 필수 인자·입력 필드 추가와 필드·값 제거는 깨짐, enum 값·union 멤버·인터페이스 추가는 클라이언트 처리에 따라 위험으로 분류합니다 (graphql-inspector 와 같은 분류)

이 도구로 할 수 있는 일

스키마 변경이 기존 클라이언트를 깨뜨리는지 배포 전에 확인합니다. 입력은 서버로 전송되지 않습니다.

  • 깨짐: 타입·필드·인자·enum 값 제거, 필수 인자·입력 필드 추가, 출력 타입 약화(T! → T), 입력 타입 강화
  • 위험: enum 값 추가, 유니언 멤버·인터페이스 추가, 기본값 변경
  • 안전: 필드·타입 추가, 선택 인자 추가, 출력 타입 강화(T → T!)
  • graphql-inspector 와 같은 분류 기준
  • '깨짐·위험만' 보기

💡 Tips

  • 응답 필드는 String → String! 로 강화하면 안전하지만 반대로 느슨해지면 깨집니다. 입력은 정반대입니다.
  • enum 값 추가는 클라이언트의 switch 가 모르는 값을 만날 수 있어 위험으로 분류합니다.
  • 필드를 바로 지우지 말고 @deprecated 로 표시한 뒤 사용이 사라지면 제거하세요.

자주 묻는 질문

실제 사용 중인 필드인지 알 수 있나요?

아니요. 스키마만 비교하므로 실제 클라이언트가 쓰는 필드인지는 알 수 없습니다. 쿼리 사용 통계와 함께 판단하세요.

연합(federation) 지시어도 비교하나요?

지시어 정의와 사용 변경은 감지하지만 연합 합성 규칙은 검증하지 않습니다.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

Kubernetes RBAC Analyzer

Paste Role, ClusterRole, RoleBinding and ClusterRoleBinding manifests to get a table of which verbs on which resources each user, group or ServiceAccount has and in what scope, with risky grants such as cluster-admin, reading Secrets, pods/exec and escalate flagged.

Example

⛔ 1 risky grant(s) — 3 binding(s), 4 subject(s)

Input — RBAC manifests (Role, ClusterRole, RoleBinding, ClusterRoleBinding)

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: dev }
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: read-pods, namespace: dev }
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: ci
    namespace: dev
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: secret-admin }
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["*"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: ops }
subjects:
  - kind: Group
…

Input — Subject to check (e.g. User:alice, Group:ops-team, ServiceAccount:dev:ci)

ServiceAccount:dev:ci

Input — Action to check: verb resource[/subresource] [namespace] (e.g. get pods dev, create pods/exec, list secrets)

list pods dev

Result — Permissions per subject

Subject | Scope | Binding | Role | Rules (apiGroup/resource: verbs)
User:alice | namespace dev | RoleBinding/read-pods | Role/pod-reader | core/pods,pods/log: get,list,watch
ServiceAccount:dev:ci | namespace dev | RoleBinding/read-pods | Role/pod-reader | core/pods,pods/log: get,list,watch
Group:ops-team | cluster-wide | ClusterRoleBinding/ops | ClusterRole/secret-admin | core/secrets: * ; core/pods/exec: create
ServiceAccount:kube-system:deployer | cluster-wide | ClusterRoleBinding/root-ci | ClusterRole/cluster-admin | */*: * ; URL *: *

Result — Permission check

Subject | Action | Result | Granted by
ServiceAccount:dev:ci | list pods (ns dev) | ✅ allowed | RoleBinding/read-pods → Role/pod-reader

What this tool does

Check who can do what, and whether any grant is excessive, from manifests alone. Your files are not uploaded.

  • Permission table: subject (User, Group, ServiceAccount:namespace:name), scope (namespace or cluster), binding, role and rules (apiGroup/resource: verbs)
  • Built-in roles: cluster-admin, admin, edit and view are modelled; a ClusterRole with aggregationRule gathers matching-label roles
  • Queries: give subject, verb, resource (including subresources such as pods/log), namespace and resourceNames to see whether it is allowed and by which binding
  • Risk checks: cluster-admin bindings, * on everything, reading Secrets, pods/exec and attach, creating pods, escalate / bind / impersonate, editing Roles and Bindings, nodes/proxy, token minting, broad groups such as system:authenticated and the default ServiceAccount
  • Warns about roleRef targets missing from the file

💡 Tips

  • Create a dedicated ServiceAccount per application and bind a Role with only the verbs it needs.
  • list or watch on secrets exposes every value even without get.
  • Permission to create pods is effectively high privilege, since hostPath or privileged pods can reach the node.

Frequently Asked Questions

Are permissions from group membership computed?

A subject's groups are unknown, so they are not; query the group itself (Group:name).

Are there deny rules?

RBAC only allows; permissions from all bindings add up, so one allow is enough.

Is my data uploaded to a server?

No. Everything is processed inside your browser; what you enter is never sent to or stored on a server, so you can safely paste data containing personal information, internal settings or API keys.

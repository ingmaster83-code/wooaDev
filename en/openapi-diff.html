OpenAPI Diff & Compatibility Check

Paste the old and new OpenAPI documents to compare endpoints, parameters, request bodies and response schemas. Changes are classified as breaking, caution or compatible, with a suggested semantic version bump. Requests and responses are judged in opposite directions.

Example

⛔ 13 breaking change(s) → major bump

Input — Old OpenAPI (YAML / JSON)

openapi: 3.0.3
info: { title: Pets, version: 1.0.0 }
paths:
  /pets:
    get:
      operationId: listPets
      parameters:
        - { name: limit, in: query, schema: { type: integer } }
        - { name: status, in: query, schema: { type: string, enum: [open, sold, pending] } }
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema: { type: array, items: { $ref: "#/components/schemas/Pet" } }
    post:
      operationId: addPet
      requestBody:
        content: { application/json: { schema: { $ref: "#/components/schemas/NewPet" } } }
      responses: { "201": { description: Created } }
  /pets/{id}:
    get:
      operationId: getPet
      parameters: [{ name: id, in: path, required: true, schema: { type: integer } }]
…

Input — New OpenAPI (YAML / JSON)

openapi: 3.0.3
info: { title: Pets, version: 1.1.0 }
paths:
  /pets:
    get:
      operationId: listPets
      parameters:
        - { name: limit, in: query, required: true, schema: { type: integer } }
        - { name: status, in: query, schema: { type: string, enum: [open, sold] } }
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema: { type: array, items: { $ref: "#/components/schemas/Pet" } }
    post:
      operationId: addPet
      requestBody:
        required: true
        content: { application/json: { schema: { $ref: "#/components/schemas/NewPet" } } }
      responses: { "201": { description: Created } }
  /pets/{id}:
    get:
      operationId: getPet
      parameters: [{ name: id, in: path, required: true, schema: { type: string } }]
…

Suggested version bump: major (MAJOR — existing clients may break)
Rules: for requests (client → server) tighter constraints break clients; for responses (server → client) weaker guarantees break them. Only the documented contract is compared, not real server behaviour

What this tool does

Check whether an API change breaks existing clients before you ship it. Your documents are not uploaded.

  • Breaking: removed endpoints or response fields, new required request parameters, stricter request types, changed response types, removed request enum values
  • Caution: added response codes, added response enum values, moved parameters
  • Compatible: added endpoints, optional parameters or response fields, description changes
  • Requests (client to server) and responses (server to client) are judged by direction, with $ref resolved before comparing
  • Recommended major / minor / patch bump and a 'breaking and caution only' view

💡 Tips

  • A request breaks when constraints grow (a new required field); a response breaks when guarantees shrink (a removed field). The directions are opposite.
  • Adding a response enum value is marked as caution because client switch statements may not handle it.
  • Use a breaking result in CI as the signal to bump the major version or introduce a /v2 path.

Frequently Asked Questions

Does it compare real server behaviour?

No. Only the contract written in the documents is compared; behaviour that differs from the docs cannot be detected.

Is it the same as oasdiff?

It follows similar classification principles but does not implement every rule. It is a quick check for the core compatibility problems.

Is my data uploaded to a server?

No. Everything is processed inside your browser; what you enter is never sent to or stored on a server, so you can safely paste data containing personal information, internal settings or API keys.

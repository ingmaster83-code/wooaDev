package.json exports Visualizer & Resolver

Paste a package.json to expand exports subpaths and conditions (import, require, types, browser, default) into a table and see which file each subpath resolves to for Node import, Node require, bundlers and TypeScript. Enter a specifier to compute the result by Node.js rules, with checks for types ordering, default position and the dual package hazard.

Example

⛔ 1 error(s), 0 warning(s) — demo-lib

Input — package.json

{
  "name": "demo-lib",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "files": [
    "dist"
  ],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    },
    "./feature": {
      "import": "./dist/feature.js",
      "require": "./dist/feature.cjs"
    },
    "./utils/*": "./dist/utils/*.js",
    "./internal/*": null,
    "./legacy/": "./legacy/"
  }
}

What this tool does

Confirm that exports resolves as intended before publishing a library. Your package.json is not uploaded.

  • Table: subpath × Node import / Node require / bundler & browser / TypeScript results
  • Resolver: computes Node.js PACKAGE_EXPORTS_RESOLVE for a specifier, environment and extra conditions (patterns, longest prefix, null blocking, array fallbacks)
  • Errors: targets not starting with ./, subpath keys mixed with conditions, folder mappings (./lib/), several * in one key, require pointing to .mjs
  • Warnings & hints: types placed late, default not last, type vs extension mismatch, ./* exposing everything, targets missing from files
  • Dual package hazard and ESM / CJS sharing one types file

💡 Tips

  • The first matching condition wins: keep 'types' first and 'default' last.
  • For TypeScript users it is safest to nest .d.mts / .d.cts types under import and require separately.
  • Adding exports blocks every deep import you do not list; make sure existing users' paths are kept.

Frequently Asked Questions

Does it check that the files exist?

It only reads package.json, so it cannot confirm existence. It compares targets with the files field to flag ones that may be left out of the publish.

Does it resolve the imports (#internal) field?

It only checks that keys start with #. The tool focuses on exports resolution.

Is my data uploaded to a server?

No. Everything is processed inside your browser; what you enter is never sent to or stored on a server, so you can safely paste data containing personal information, internal settings or API keys.

GraphQL Schema Diff & Compatibility Check

Compare old and new GraphQL SDL to classify changes to types, fields, arguments, enum values, unions and interfaces as breaking, dangerous or safe. Response fields and input arguments are judged in opposite directions when types get stricter.

Example

⛔ 8 breaking · 4 dangerous

Input — Old schema (SDL)

type Query {
  user(id: ID!): User
  users(role: Role, limit: Int = 10): [User!]!
  legacy: String
}
type User {
  id: ID!
  name: String
  email: String!
  role: Role!
  age: Int
}
enum Role { ADMIN EDITOR VIEWER }
input Filter { text: String, active: Boolean }
union Result = User | Post
type Post { id: ID! }
interface Entity { id: ID! }

Input — New schema (SDL)

type Query {
  user(id: String!, expand: Boolean!): User
  users(role: Role, limit: Int = 25): [User]
  version: String
}
type User implements Entity {
  id: ID!
  name: String!
  email: String
  role: Role!
  nickname: String
}
enum Role { ADMIN EDITOR GUEST }
input Filter { text: String!, active: Boolean, tag: String }
union Result = User | Post | Comment
type Post { id: ID! }
type Comment { id: ID! }
interface Entity { id: ID! }

Result — Changes

Verdict | Where | Change
⛔ breaking | Query.user(id) | argument type ID! → String!
⛔ breaking | Query.user(expand) | argument added (required)
⛔ breaking | Query.users | type [User!]! → [User]
⛔ breaking | Query.legacy | field removed
⛔ breaking | User.email | type String! → String
⛔ breaking | User.age | field removed
⛔ breaking | Role.VIEWER | enum value removed
⛔ breaking | Filter.text | type String → String!
⚠️ dangerous | Query.users(limit) | default 10 → 25 (calls that omit the argument change behaviour)
⚠️ dangerous | User | now implements interface Entity (results of … on Entity queries can change)
⚠️ dangerous | Role.GUEST | enum value added (client switches may not handle it)
⚠️ dangerous | Result | union member Comment added (clients must handle the new type)
✅ safe | Query.version | field added
✅ safe | User.name | type String → String! (stronger guarantee)
✅ safe | User.nickname | field added
✅ safe | Filter.tag | input field added (optional)
✅ safe | Comment | type type added

Result — Summary

⛔ 8 breaking · 4 dangerous · 5 safe
Rules: for response fields a stricter type (T → T!) is safe and a looser one (T! → T) breaks; inputs (arguments, input fields) are the reverse. Adding required arguments or input fields and removing fields or values break clients; adding enum values, union members or interfaces is dangerous depending on client handling (the same classes as graphql-inspector)

What this tool does

Check whether a schema change breaks existing clients before deploying it. Your input is not uploaded.

  • Breaking: removed types, fields, arguments or enum values, new required arguments or input fields, weaker output types (T! → T), stricter input types
  • Dangerous: added enum values, union members or interfaces, changed default values
  • Safe: added fields or types, optional arguments, stricter output types (T → T!)
  • Same classification principles as graphql-inspector
  • 'Breaking and dangerous only' view

💡 Tips

  • Making a response field String → String! is safe but loosening it breaks clients; inputs work the opposite way.
  • Adding an enum value is dangerous because client switch statements may meet an unknown value.
  • Mark a field @deprecated first and remove it only once nothing uses it.

Frequently Asked Questions

Can it tell whether a field is actually used?

No. It compares schemas only, so it cannot know which fields real clients query. Combine it with query usage statistics.

Does it compare federation directives?

Directive definition and usage changes are detected, but federation composition rules are not validated.

Is my data uploaded to a server?

No. Everything is processed inside your browser; what you enter is never sent to or stored on a server, so you can safely paste data containing personal information, internal settings or API keys.

JSON Schema Diff — Changes & Compatibility Risk

Compares two JSON Schemas, finds added/removed properties and changes in required, type, enum and constraints, and tells you whether they break compatibility for requests or responses.

Example

⚠️ Breaking 4 · Caution 0 · Safe 1

Input — Old schema (A)

{
  "type": "object",
  "required": ["id", "name"],
  "properties": {
    "id": { "type": "integer" },
    "name": { "type": "string", "maxLength": 50 },
    "status": { "enum": ["active", "inactive"] },
    "age": { "type": "integer", "minimum": 0 }
  }
}

Input — New schema (B)

{
  "type": "object",
  "required": ["id", "name", "email"],
  "properties": {
    "id": { "type": "string" },
    "name": { "type": "string", "maxLength": 30 },
    "email": { "type": "string", "format": "email" },
    "status": { "enum": ["active", "inactive", "banned"] },
    "age": { "type": "integer", "minimum": 18 }
  }
}

Result — Changes & risk

Risk | Path | Change | Before | After
🔴 Breaking | id | Type changed | integer | string
🔴 Breaking | name | maxLength became stricter | 50 | 30
🔴 Breaking | age | minimum became stricter | 0 | 18
🔴 Breaking | email | Required property added |  | string
🟢 Safe | status | enum value(s) added |  | banned

What this tool does

The scariest part of changing an API schema is breaking existing clients. Give it two versions and it shows what changed and whether the change is risky.

  • Property added/removed, required ↔ optional, type changes (widened/narrowed), enum values added/removed
  • Constraint changes: minimum/maximum, minLength/maxLength, pattern, format, minItems/maxItems, additionalProperties…
  • Pick what the schema describes: a request (data clients send) or a response (data clients receive) — the same change carries different risk
  • Rated 🔴 Breaking / 🟡 Caution / 🟢 Safe, sorted by risk
  • $ref and allOf are expanded before comparing; oneOf/anyOf changes are flagged for manual review

For plain value comparison use the JSON Diff tool.

💡 Tips

  • For request schemas, new required properties and stricter constraints are the riskiest; for responses, removed required properties and type changes are.
  • Adding an enum value is safe in a request schema but flagged as caution in a response, where clients may not handle it.
  • The rating is a heuristic — combine it with contract tests before releasing.

Frequently Asked Questions

Why does risk differ between requests and responses?

Making a request schema stricter can reject data existing clients send; loosening a response schema can hand clients data they don't expect. Risk points in opposite directions.

Can I diff whole OpenAPI documents?

Paste the schema fragments you want to compare (the content of components.schemas.X) rather than the full document. Internal $refs are resolved only within each fragment.

Is my data uploaded to a server?

No. Everything is processed inside your browser; what you enter is never sent to or stored on a server, so you can safely paste data containing personal information, internal settings or API keys.

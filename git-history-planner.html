Git 병합 · 리베이스 시뮬레이터 — 커밋 그래프 미리보기

공통 커밋과 두 브랜치의 커밋 수를 정하고 작업을 고르면 실행 전후의 커밋 그래프를 ASCII로 그려 보여 줍니다. 어떤 커밋의 해시가 바뀌는지, 어떤 명령을 쓰는지도 알려 줍니다.

사용 예시

✅ merge 결과를 그렸습니다

결과 — 커밋 그래프 (작업 전 → 후)

■ 작업 전
          D---E
         /
A---B---C---F---G
  main → G  (HEAD)
  feature → E

■ 작업 후
          D---E
         /     \
A---B---C---F---G---H
  main → H  (HEAD)
  feature → E

결과 — 실행할 명령어

git switch main
git merge feature

이 도구로 할 수 있는 일

merge와 rebase의 차이는 말로 읽을 때보다 그림으로 볼 때 이해가 빠릅니다. 숫자만 바꾸면 여러 상황을 바로 비교할 수 있습니다.

  • 입력: 분기점까지의 공통 커밋 수, feature·main 에서 분기 이후 커밋 수, 브랜치 이름
  • 작업: merge(빨리감기 가능 시 자동), --no-ff, --squash, rebase, rebase 후 --ff-only, cherry-pick
  • 작업 전·후 커밋 그래프와 브랜치 포인터(HEAD) 위치를 ASCII로 표시
  • 커밋별 변화 표: 그대로 / ♻️ 새 해시로 다시 만들어짐 / 🆕 새로 생김
  • 실행할 명령어, 강제 푸시 필요 여부, 충돌 가능성, 복구 방법을 함께 안내

💡 Tips

  • 공유 브랜치에는 merge 를, 아직 push 하지 않은 개인 브랜치 정리는 rebase 를 쓰는 것이 일반적인 규칙입니다.
  • GitHub의 Squash and merge 는 --squash 와 같습니다. 합친 뒤 작업 브랜치는 삭제하세요.
  • rebase 가 꼬이면 git rebase --abort, 이미 끝났다면 git reflog 로 이전 위치를 찾으세요.

자주 묻는 질문

rebase 후 왜 강제 푸시가 필요한가요?

rebase 는 커밋을 복사해 새 해시로 다시 만들기 때문에 원격의 옛 커밋과 이력이 갈라집니다. git push --force-with-lease 가 필요하고, 다른 사람이 쓰는 브랜치에는 하지 마세요.

merge --no-ff 는 언제 쓰나요?

빨리감기가 가능해도 병합 커밋을 남겨 기능 단위 이력을 보존하고 싶을 때 씁니다.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

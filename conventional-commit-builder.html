Conventional Commits 작성기 · 검사기

타입, 범위, 설명, 본문, 호환성 파괴(BREAKING CHANGE), 이슈 참조를 입력해 Conventional Commits 형식의 커밋 메시지를 만들고, 이미 쓴 메시지가 규칙에 맞는지 검사합니다.

사용 예시

✅ Conventional Commits 규칙을 모두 지켰습니다

입력 — 설명 (제목 한 줄)

add OAuth login with PKCE

입력 — 범위 (scope, 선택)

auth

입력 — 본문 (선택)

Replaces the implicit flow. Tokens are now exchanged on the server.

입력 — 이슈 참조 (예: 123, 456)

123

입력 — 검사할 커밋 메시지

Feat(Auth): Added new login page.
this is the body without a blank line before it

결과 — 커밋 메시지

feat(auth): add OAuth login with PKCE

Replaces the implicit flow. Tokens are now exchanged on the server.

Refs #123

결과 — 분석

항목 | 값
타입 | feat
범위 | auth
설명 | add OAuth login with PKCE
본문 | Replaces the implicit flow. Tokens are now exchanged on the server.
푸터 | Refs #123
호환성 파괴 | 아니오
SemVer 영향 | minor (0.X.0) — 기능 추가

이 도구로 할 수 있는 일

커밋 메시지를 일정한 형식으로 쓰면 변경 이력과 버전 올림을 자동화할 수 있습니다. 형식을 외우지 않아도 되도록 만들어 줍니다.

  • 만들기: 타입(feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert), 범위, 설명, 본문, 호환성 파괴, 이슈 번호(Fixes/Refs)
  • 검사: 첫 줄 형식, 타입 소문자, 표준 타입 여부, 설명 끝 마침표·대문자 시작·과거형, 콜론 뒤 공백, 제목 길이, 제목 다음 빈 줄
  • SemVer 영향: BREAKING → major, feat → minor, fix → patch, 그 외 변화 없음
  • 규칙에 맞게 고친 메시지를 자동으로 제안
  • 제목 최대 길이 설정(기본 72자)

💡 Tips

  • 제목은 명령형 현재 시제로 씁니다. 'added login' 보다 'add login' 입니다.
  • 호환성이 깨지면 타입 뒤에 !를 붙이고 푸터에 BREAKING CHANGE: 설명을 적으세요.
  • commitlint 와 같은 규칙을 팀에서 쓴다면 이 도구로 먼저 메시지를 만들어 보세요.

자주 묻는 질문

scope 는 꼭 써야 하나요?

선택입니다. 모노레포나 큰 프로젝트에서는 변경 위치를 알려 줘 유용하지만 작은 프로젝트에서는 생략해도 됩니다.

한국어로 써도 되나요?

형식(타입: 설명)만 지키면 설명은 한국어여도 됩니다. 다만 명령형·마침표 같은 영어 문체 규칙은 팀에서 정하세요.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

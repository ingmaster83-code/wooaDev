릴리스 플래너 — 다음 버전과 CHANGELOG 자동 생성

Conventional Commits 형식의 커밋 목록을 붙여 넣으면 다음 버전(major/minor/patch)을 계산하고, 기능·수정별로 분류한 CHANGELOG 초안과 태그·푸시 명령어까지 만들어 줍니다.

사용 예시

✅ 1.4.2 → 2.0.0 (major)

입력 — 커밋 메시지 목록 (한 줄에 하나, 해시 접두 가능)

a1b2c3d feat(auth): add OAuth login with PKCE
e4f5a6b fix(api): handle empty response from /items (#214)
7c8d9e0 perf(db): add index on orders.created_at
1f2e3d4 docs: explain deployment steps
5a6b7c8 refactor(core)!: drop the legacy session store
9d0e1f2 fix: typo in error message
3c4d5e6 chore(deps): bump express to 4.19.2
WIP stuff
8b9c0d1 feat(ui): dark mode toggle (closes #230)

이 도구로 할 수 있는 일

릴리스할 때마다 git log 를 읽고 버전을 정하고 노트를 쓰는 일을 자동화합니다. 커밋만 붙여 넣으면 됩니다.

  • 버전 결정: BREAKING CHANGE/! → major, feat → minor, fix·perf → patch, docs·chore 만 있으면 릴리스 없음
  • 0.x 버전은 호환성 파괴를 minor 로 올리는 옵션, 프리릴리스(rc·beta) 번호 증가 처리
  • CHANGELOG: 새 기능/버그 수정/성능/되돌림 분류 또는 Keep a Changelog(Added/Changed/Fixed)
  • 저장소 URL을 주면 이슈(#123)·커밋 해시·버전 비교 링크 포함
  • 형식이 맞지 않는 커밋은 제외하고 알려 줌, git tag·push 명령어 제공

함께 쓰면 좋은 도구

💡 Tips

  • git log --oneline 결과(해시 + 메시지)를 그대로 붙여 넣을 수 있습니다.
  • 자동 생성된 노트는 초안입니다. 사용자가 이해할 수 있는 문장으로 다듬어 릴리스하세요.
  • 기능 브랜치를 squash merge 한다면 PR 제목을 Conventional Commits 형식으로 쓰게 하세요.

자주 묻는 질문

커밋이 규칙을 안 지켰으면요?

형식에 맞지 않는 줄은 버전 계산과 노트에서 제외되고 목록에 표시됩니다. 팀에서 커밋 메시지 규칙을 정해 두면 가장 정확합니다.

1.0.0 이전에는 어떻게 되나요?

0.x 는 안정 API가 아니라는 SemVer 규칙에 따라 호환성 파괴도 minor 로 올리는 관행이 있습니다. 옵션으로 선택하세요.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

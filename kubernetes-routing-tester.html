Ingress · Service 라우팅 테스터

Ingress 와 Service 매니페스트를 붙여 넣고 요청 URL 을 한 줄에 하나씩 입력하면 호스트(정확·와일드카드), 경로(Exact·Prefix·정규식), 가장 긴 일치 규칙, 대상 Service 포트와 파드 targetPort 까지 어떻게 라우팅되는지 보여 줍니다.

사용 예시

⛔ 라우팅 실패 1건 — 요청 8개

입력 — Ingress · Service · Deployment 매니페스트 (YAML)

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.example.com]
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend: { service: { name: api, port: { number: 8080 } } }
          - path: /static
            pathType: Prefix
            backend: { service: { name: static, port: { name: http } } }
          - path: /static/private
            pathType: Exact
            backend: { service: { name: admin, port: { number: 80 } } }
          - path: /
            pathType: Prefix
            backend: { service: { name: web, port: { number: 80 } } }
    - host: "*.example.com"
      http:
        paths:
…

입력 — 테스트할 요청 (한 줄에 URL 하나)

https://app.example.com/
https://app.example.com/api/users
https://app.example.com/static/logo.png
https://app.example.com/static/private
https://app.example.com/static/private/x
http://app.example.com/staticfile
https://other.example.com/anything
https://unknown.org/

결과 — 라우팅 결과

요청 | 일치한 규칙 | 백엔드 | 비고 | 클래스
https://app.example.com/ | main · app.example.com / (Prefix) | web:80 → pod:http | rewrite → / | nginx
https://app.example.com/api/users | main · app.example.com /api(/|$)(.*) (ImplementationSpecific) | api:8080 → pod:3000 | rewrite → /users | nginx
https://app.example.com/static/logo.png | main · app.example.com /static (Prefix) | static:http → pod:80 | rewrite → / | nginx
https://app.example.com/static/private | main · app.example.com /static/private (Exact) | admin:80 | Service "admin" 이 이 파일에 없음 · rewrite → / | nginx
https://app.example.com/static/private/x | main · app.example.com /static (Prefix) | static:http → pod:80 | rewrite → / | nginx
http://app.example.com/staticfile | main · app.example.com / (Prefix) | web:80 → pod:http | rewrite → / · TLS 호스트라 https 로 리다이렉트(308)될 수 있음 | nginx
https://other.example.com/anything | main · *.example.com / (Prefix) | wildcard:80 | Service "wildcard" 이 이 파일에 없음 · rewrite → / | nginx
https://unknown.org/ | — | — | ⛔ 일치하는 규칙 없음 → 404 (default backend 가 있으면 그쪽) |

결과 — 점검 결과

ℹ️ ImplementationSpecific 경로 "/api(/|$)(.*)" 의 해석은 Ingress 컨트롤러마다 다릅니다 (nginx 는 접두사, use-regex 면 정규식). 이 도구는 nginx 동작을 따릅니다
우선순위: 정확한 호스트 > 와일드카드 호스트 > 호스트 없음, 같은 호스트 안에서는 Exact > 가장 긴 Prefix 순서입니다. Prefix 는 경로 요소 단위로 비교해 /static 은 /staticfile 과 일치하지 않습니다

이 도구로 할 수 있는 일

Ingress 를 클러스터에 적용하기 전에 어떤 요청이 어느 서비스로 갈지 미리 확인합니다. 매니페스트는 서버로 전송되지 않습니다.

  • 호스트: 정확 일치 > 와일드카드(*.example.com 은 한 단계) > 호스트 없는 규칙, 대소문자 무시
  • 경로: Exact 는 완전 일치, Prefix 는 경로 요소 단위 접두사(/foo 는 /foo/bar 와 일치하고 /foobar 와는 불일치), / 는 전체, 가장 긴 규칙 우선
  • ImplementationSpecific: nginx 동작 기준으로 접두사 또는 정규식(use-regex)으로 해석하고 컨트롤러마다 다르다고 안내
  • 백엔드: Service 이름·포트(이름 또는 번호), Service 포트 → targetPort, selector 와 일치하는 파드, defaultBackend
  • 부가 정보: nginx rewrite-target 결과 경로, TLS 호스트의 http → https 리다이렉트, 중복 규칙, ingressClassName 누락

💡 Tips

  • 같은 경로에 Exact 와 Prefix 가 있으면 Exact 가 우선입니다.
  • ImplementationSpecific 은 컨트롤러 구현에 맡기는 값입니다. 정규식이 필요하면 컨트롤러 문서의 어노테이션을 확인하세요.
  • 와일드카드 호스트는 *.example.com 이 a.example.com 과는 일치하지만 example.com 이나 a.b.example.com 과는 일치하지 않습니다.

자주 묻는 질문

모든 Ingress 컨트롤러와 같은 결과인가요?

표준 규칙(호스트, pathType 우선순위)은 같지만 ImplementationSpecific 과 어노테이션은 컨트롤러마다 다릅니다. 이 도구는 ingress-nginx 동작을 따릅니다.

Service 가 파일에 없으면요?

백엔드 이름과 포트만 표시하고 'Service 가 이 파일에 없음' 이라고 알려 줍니다.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

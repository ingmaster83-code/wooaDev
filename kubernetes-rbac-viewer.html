Kubernetes RBAC 권한 분석기

Role, ClusterRole, RoleBinding, ClusterRoleBinding 매니페스트를 붙여 넣으면 사용자·그룹·ServiceAccount 별로 어떤 범위에서 어떤 리소스에 어떤 동사가 허용되는지 표로 정리하고, cluster-admin 바인딩, Secret 읽기, pods/exec, escalate 같은 위험한 권한을 찾아 줍니다.

사용 예시

⛔ 위험한 권한 1건 — 바인딩 3개, 주체 4개

입력 — RBAC 매니페스트 (Role · ClusterRole · RoleBinding · ClusterRoleBinding)

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: dev }
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: read-pods, namespace: dev }
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: ci
    namespace: dev
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: secret-admin }
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["*"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: ops }
subjects:
  - kind: Group
…

입력 — 권한을 확인할 주체 (예: User:alice · Group:ops-team · ServiceAccount:dev:ci)

ServiceAccount:dev:ci

입력 — 확인할 동작: 동사 리소스[/하위리소스] [네임스페이스] (예: get pods dev · create pods/exec · list secrets)

list pods dev

결과 — 주체별 권한

주체 | 범위 | 바인딩 | 역할 | 권한 (apiGroup/리소스: 동사)
User:alice | 네임스페이스 dev | RoleBinding/read-pods | Role/pod-reader | core/pods,pods/log: get,list,watch
ServiceAccount:dev:ci | 네임스페이스 dev | RoleBinding/read-pods | Role/pod-reader | core/pods,pods/log: get,list,watch
Group:ops-team | 클러스터 전체 | ClusterRoleBinding/ops | ClusterRole/secret-admin | core/secrets: * ; core/pods/exec: create
ServiceAccount:kube-system:deployer | 클러스터 전체 | ClusterRoleBinding/root-ci | ClusterRole/cluster-admin | */*: * ; URL *: *

결과 — 권한 확인 결과

주체 | 동작 | 결과 | 근거
ServiceAccount:dev:ci | list pods (ns dev) | ✅ 허용 | RoleBinding/read-pods → Role/pod-reader

이 도구로 할 수 있는 일

누가 무엇을 할 수 있는지, 과도한 권한이 없는지 매니페스트만으로 점검합니다. 파일은 서버로 전송되지 않습니다.

  • 권한표: 주체(User, Group, ServiceAccount:네임스페이스:이름), 범위(네임스페이스/클러스터), 바인딩, 역할, 규칙(apiGroup/리소스: 동사)
  • 내장 역할: cluster-admin, admin, edit, view 규칙 반영, aggregationRule 이 있는 ClusterRole 은 레이블이 맞는 역할을 합침
  • 질의: 주체, 동사, 리소스(하위 리소스 pods/log), 네임스페이스, resourceNames 를 지정해 허용 여부와 근거 바인딩 확인
  • 위험 점검: cluster-admin 바인딩, 모든 리소스에 *, Secret 읽기, pods/exec·attach, pods 생성, escalate/bind/impersonate, Role·Binding 수정, nodes/proxy, 토큰 발급, system:authenticated 같은 넓은 그룹, default ServiceAccount
  • roleRef 대상 누락 경고

💡 Tips

  • 애플리케이션마다 전용 ServiceAccount 를 만들고 필요한 동사만 가진 Role 을 바인딩하세요.
  • secrets 에 list/watch 가 있으면 get 이 없어도 모든 값을 읽을 수 있습니다.
  • pods 생성 권한은 hostPath·privileged 파드로 노드에 접근할 수 있어 사실상 높은 권한입니다.

자주 묻는 질문

그룹으로 얻는 권한도 계산하나요?

주체가 속한 그룹은 알 수 없어 계산하지 않습니다. 그룹 자체(Group:이름)를 주체로 질의하세요.

거부(deny) 규칙은 없나요?

RBAC 은 허용만 있습니다. 여러 바인딩의 권한이 합쳐지므로 하나라도 허용하면 허용됩니다.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

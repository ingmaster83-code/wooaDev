GitLab CI 파이프라인 검증기

.gitlab-ci.yml 을 붙여 넣으면 잡 표와 스테이지 실행 순서를 보여 주고, 없는 스테이지, script 누락, needs 의 뒤 스테이지·순환, extends 대상, rules 와 only 혼용, 불리언 변수, retry·when 오류를 줄 번호로 알려 줍니다.

사용 예시

⛔ 오류 6건 · 경고 1건 — 잡 3개

입력 — .gitlab-ci.yml

stages: [build, test, deploy]

variables:
  NODE_ENV: production
  DEBUG: true

.node:
  image: node:latest
  before_script:
    - npm ci

build:
  extends: .node
  stage: build
  script:
    - npm run build
  artifacts:
    paths: [dist/]

test:
  extends: .nodejs
  stage: test
  script: npm test
  needs: [build, deploy]
  only: [main]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy:
  stage: deploy
  retry: 5
  when: delayed
  script:
    - ./deploy.sh
  environment: production

결과 — 잡 목록 (스테이지 순)

잡 | 스테이지 | 이미지 | script 줄 | needs | 실행 조건 | 줄
build | build | node:latest | 1 | — | on_success | 12
test | test | — | 1 | build, deploy | rules | 20
deploy | deploy | — | 1 | — | delayed | 29

결과 — 점검 결과

⛔ 줄 5: 변수 DEBUG 의 값이 불리언입니다. GitLab 변수 값은 문자열이어야 하므로 따옴표로 감싸세요 ("true")
⚠️ 줄 13: 이미지 "node:latest" 는 태그가 없거나 latest 입니다. 버전을 고정하세요
ℹ️ 줄 17: artifacts 에 expire_in 이 없으면 기본 만료(30일, 인스턴스 설정)만큼 저장 공간을 차지합니다
⛔ 줄 21: extends 의 ".nodejs" 잡(템플릿)이 없습니다
⛔ 줄 24: needs "deploy"(deploy)는 뒤 스테이지(test)보다 늦어서 기다릴 수 없습니다
⛔ 줄 26: 잡 "test" 에 rules 와 only/except 를 함께 쓸 수 없습니다
⛔ 줄 31: retry 는 0~2 사이여야 합니다 (현재 5)
⛔ 줄 32: when: delayed 에는 start_in 이 필요합니다 (예: 30 minutes)

이 도구로 할 수 있는 일

push 해서 파이프라인이 만들어지지 않는 오류를 보기 전에 구조를 점검합니다. 파일은 서버로 전송되지 않습니다.

  • 잡 표: 스테이지(기본 .pre·build·test·deploy·.post), 이미지, script 줄 수, needs, 실행 조건, 줄 번호
  • 상속: extends 체인을 해석해 template(.이름) 의 script·image 를 반영, 순환·없는 대상 감지
  • 참조: stage 정의, needs 대상 존재·뒤 스테이지·순환, dependencies 는 앞 스테이지 잡
  • 규칙: rules 키·when 값, rules 와 only/except 혼용 금지, rules:if 의 따옴표·정규식(/패턴/), when: delayed 의 start_in, retry 0~2
  • 변수·보안: 변수 이름, 불리언 값(문자열이어야 함), 평문 비밀, latest 이미지, artifacts 의 paths·expire_in

💡 Tips

  • 변수 값은 문자열이어야 합니다. DEBUG: true 대신 DEBUG: "true" 로 쓰세요.
  • needs 를 쓰면 스테이지를 기다리지 않고 DAG 로 실행되어 파이프라인이 빨라집니다. 단 앞쪽 스테이지의 잡만 지정할 수 있습니다.
  • include 로 가져온 템플릿은 이 도구가 볼 수 없어 해당 참조는 경고로만 표시합니다.

자주 묻는 질문

YAML 앵커와 !reference 도 되나요?

앵커와 병합 키(<<)는 해석합니다. !reference 는 값 해석 없이 통과시키며 참조 대상은 확인하지 않습니다.

실제 GitLab 의 CI Lint 와 같은가요?

서버 쪽 전체 검증은 아니며 흔한 구조 오류를 빠르게 찾는 용도입니다. 최종 확인은 프로젝트의 CI Lint 로 하세요.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.

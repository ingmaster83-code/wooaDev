Kubernetes 리소스 계산기 — requests · limits · QoS

컨테이너별 CPU/메모리 requests와 limits를 입력하면 파드 합계, QoS 클래스(Guaranteed/Burstable/BestEffort), 레플리카·HPA 최대치에서 필요한 노드 수와 resources YAML을 계산합니다.

사용 예시

✅ 파드 1개 요청 320m CPU · 352Mi · QoS Burstable

입력 — 컨테이너 (한 줄에 하나: 이름 CPU요청 CPU한도 메모리요청 메모리한도, 없으면 -)

app 250m 500m 256Mi 512Mi
sidecar 50m 100m 64Mi 128Mi
log-agent 20m - 32Mi 64Mi

결과 — 컨테이너별 리소스

컨테이너 | CPU 요청 / 한도 | 메모리 요청 / 한도
app | 250m / 500m | 256Mi / 512Mi
sidecar | 50m / 100m | 64Mi / 128Mi
log-agent | 20m / — | 32Mi / 64Mi

결과 — 파드·배포 합계

항목 | 값
파드 1개 요청 (CPU / 메모리) | 320m / 352Mi
파드 1개 한도 (CPU / 메모리) | 600m / 704Mi
QoS | Burstable — 요청 < 한도(또는 일부만 지정) — 노드 자원이 부족하면 중간 우선순위로 쫓겨남
레플리카 3개 요청 합계 | 960m / 1Gi
레플리카 3개 한도 합계 | 1800m / 2.1Gi
노드 1대당 들어가는 파드 수 | 11개 (CPU 기준 11, 메모리 기준 36)
레플리카 3개에 필요한 노드 | 1대 이상
HPA 최대 10개일 때 필요한 노드 | 1대 이상
노드 사용 효율 (병목 자원) | CPU · 100% CPU, 30% 메모리

이 도구로 할 수 있는 일

리소스 설정은 단위(m, Mi, Gi, M)를 헷갈리기 쉽고, 잘못 설정하면 스케줄링 실패(Pending)나 OOMKilled 로 이어집니다.

  • 입력: 한 줄에 컨테이너 하나 — 이름, CPU 요청, CPU 한도, 메모리 요청, 메모리 한도 (없으면 -)
  • 단위: 250m·0.5·2 코어, Ki·Mi·Gi·Ti, K·M·G·T, 지수 표기(129e6) 인식
  • 계산: 파드 합계, 레플리카 합계, QoS 클래스(요청 없이 한도만 있으면 요청 = 한도), 노드 할당량·시스템 몫을 반영한 노드당 파드 수와 필요 노드 수(HPA 최대 포함)
  • 컨테이너별 resources YAML 블록 생성
  • 🚨 한도 < 요청, 메모리 한도 없음, CPU 요청 없음, 한도/요청 비율 과다, 노드보다 큰 파드, 단위 실수 의심 경고

💡 Tips

  • CPU 한도는 초과하면 종료가 아니라 스로틀링(느려짐)이고, 메모리 한도 초과는 OOMKilled 입니다.
  • 스케줄러는 requests 합계로 배치하므로 requests 가 너무 크면 노드가 놀고, 너무 작으면 과밀해집니다.
  • 노드 할당 가능량은 kubectl describe node 의 Allocatable 값을 넣으세요.

자주 묻는 질문

QoS 클래스가 왜 중요한가요?

노드 자원이 부족할 때 BestEffort → Burstable → Guaranteed 순으로 파드가 쫓겨납니다. 중요한 서비스는 requests = limits 로 Guaranteed 를 만들 수 있습니다.

250m 은 무슨 뜻인가요?

1000m = 1 코어이므로 250m 은 0.25 코어입니다. 메모리의 Mi 는 2의 거듭제곱(1Mi=1,048,576바이트), M 은 10의 거듭제곱 단위입니다.

입력한 데이터가 서버로 전송되나요?

아니요. 모든 처리는 브라우저 안에서만 이루어지며 입력한 내용은 서버로 전송되거나 저장되지 않습니다. 개인정보나 사내 설정값, API 키가 들어 있는 데이터도 안심하고 붙여 넣을 수 있습니다.
